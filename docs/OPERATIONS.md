# Operations

How Body Shop is deployed, rolled back, restored and diagnosed. The blueprint
itself is [render.yaml](../render.yaml); this is the part that does not fit in
comments.

## What runs where

| Piece | Where | Notes |
| --- | --- | --- |
| Web service | Render, `plan: free` | `gunicorn wsgi:application`, from `render.yaml`. |
| Postgres | Supabase | The same project that holds auth. |
| Auth | Supabase (GoTrue) | The browser talks to it directly; Flask only verifies tokens. |
| Exercise photographs | jsDelivr, pinned commit | Not our origin. Disclosed on `/privacy`. |
| Errors | Sentry | Only when `BODYSHOP_SENTRY_DSN` is set. |

**Render holds no data.** Every persistent thing is in Supabase, and the
instance filesystem is ephemeral by design — production refuses to boot on a
SQLite `DATABASE_URL` for exactly this reason. That is what makes the web
service disposable: it can be destroyed and re-created from the blueprint
without losing a set.

## First deploy

The order matters, and two of these steps are traps that only bite once.

**1. Get both connection strings.** Supabase → Project Settings → Database.

| Use | Pooler | Port |
| --- | --- | --- |
| The app (`DATABASE_URL` on Render) | Transaction | 6543 |
| Migrations, `pg_dump`, the test suite | Session or direct | 5432 |

`app/db.py` passes `prepare_threshold=None` and `NullPool` because the app runs
behind the transaction pooler, which cannot carry prepared statements across
the connections it multiplexes.

**2. Migrate *before* the first deploy**, from your machine:

```bash
DATABASE_URL='<session-pooler-url>' python -m flask --app app upgrade-db
```

**This is the trap.** A web service that boots against an unmigrated database
starts fine and serves a 500 from every authenticated route — `/healthz` will
still answer 200, because it deliberately touches no database.

Migrations are not a Render hook because `preDeployCommand` is a paid-tier
feature (so is Shell), and because DDL through a transaction-mode pooler is not
something to rely on. Even on Starter, point the hook at the session pooler.

**3. Create the service.** Render → New → Blueprint → this repository. Fill in
every value marked `sync: false`:

| Variable | From |
| --- | --- |
| `DATABASE_URL` | Supabase, **transaction** pooler (6543) |
| `BODYSHOP_SUPABASE_URL` | Supabase → Project Settings → API |
| `BODYSHOP_SUPABASE_ANON_KEY` | same page — public by design |
| `BODYSHOP_SUPABASE_SERVICE_ROLE_KEY` | same page — **secret**, used only by `DELETE /api/account` |
| `BODYSHOP_SUPABASE_JWT_SECRET` | only for older projects signing HS256; leave unset to verify against the published JWKS |
| `BODYSHOP_CONTACT_EMAIL` | you — production will not boot without it |
| `BODYSHOP_SENTRY_DSN` | Sentry, optional |

`BODYSHOP_SECRET_KEY` is generated by Render. Do not paste one.

**4. Point Supabase at the new hostname.** Supabase → Authentication → URL
Configuration:

- Site URL: `https://<name>.onrender.com`
- Redirect URLs: `https://<name>.onrender.com/verify` and
  `https://<name>.onrender.com/reset-password`

**This is the second trap.** Confirmation and recovery emails link to whatever
is configured here, so until this is done every new signup receives an email
pointing at `localhost`. Nothing in the app can detect this — it fails in the
user's inbox.

**5. Check it.**

```bash
curl -s https://<name>.onrender.com/healthz
# {"status":"ok","version":"0.1.0"}
```

Then sign up with a real address, confirm the link lands on the Render host,
log a set, and check `/summary` grades it.

## Deploying a change

1. **Wait for CI green on `main`** — specifically the Postgres job. The SQLite
   job cannot catch a dialect difference by construction, and production is
   Postgres. This is the whole gate.
2. **If the change includes a migration, run it first**, against the session
   pooler, as in step 2 above. A rolling deploy otherwise runs new code against
   the old schema for the length of the rollout.
3. Push to `main`. Render builds and swaps.

## Rolling back

Render's dashboard → the service → Rollback to a previous deploy.

**Code rolls back; migrations do not.** If the deploy included a revision, the
new schema stays. That is fine for an additive revision and is not fine for a
destructive one — check which kind it was before assuming the rollback is
complete. `downgrade_db` exists in `app/db.py` and deliberately has no CLI
wrapper: backing a schema out is an act you should have to write code to
perform.

## The restore drill

Supabase takes the backups. This is the part that proves they are worth
something, because **an untested backup is a belief rather than a backup.**

Never restore over production. Every step below targets a scratch database.

```bash
# 1. Dump production, through the SESSION pooler (5432).
pg_dump --no-owner --no-privileges --format=custom \
        --file=bodyshop-$(date +%F).dump '<session-pooler-url>'

# 2. Restore into a scratch database.
pg_restore --no-owner --no-privileges --dbname='<scratch-url>' \
           bodyshop-$(date +%F).dump

# 3. The restored schema must be at head.
DATABASE_URL='<scratch-url>' python -m alembic current
# ...expect the newest revision in migrations/versions/, marked (head)

# 4. Row counts must match the source.
for url in '<session-pooler-url>' '<scratch-url>'; do
  psql "$url" -Atc 'SELECT
      (SELECT count(*) FROM "user"),
      (SELECT count(*) FROM workout_entry),
      (SELECT count(*) FROM workout_set)'
done
```

**5. Optionally**, run the suite against the restored copy for schema sanity:

```bash
BODYSHOP_TEST_DATABASE_URL='<scratch-url>' pytest
```

This is **last**, because the suite truncates `workout_entry` between tests. It
destroys the restored data, which is why the copy is scratch and why nothing
after it can be checked.

**Last successful drill:** _never run_

Update that line when you run it. A date that has gone stale is a signal; a
line that says nothing is not.

## Upgrading off the free tier

The free instance sleeps after 15 minutes idle, and the next request pays
roughly a 50-second cold start. For a workout log — opened mid-set, with a
barbell on the floor — that is the difference between using the app and giving
up on it.

The change is one line in `render.yaml`:

```yaml
    plan: starter        # was: free
```

Starter also unlocks `preDeployCommand`, so migrations can move into the deploy
if you want them there. Point it at the session pooler, not at the
`DATABASE_URL` the web service uses.

## When something breaks

Work down this list; it is ordered so each step rules something out.

1. **`curl https://<host>/healthz`.** Answers → the process is up and serving,
   so the deploy is not the problem. Does not answer → check Render's logs for a
   boot failure; a `ConfigError` there names the missing variable outright.
2. **`/healthz` answers but the app 500s → it is the database.** That is exactly
   the split the health check was designed to give you, which is why it opens no
   connection. Check the Supabase dashboard, then whether a migration is
   pending.
3. **Sentry.** Stack trace, request path, release. If nothing is there, check
   that `BODYSHOP_SENTRY_DSN` is actually set on the service.
4. **Render's logs.** Everything gunicorn wrote, retained 7 days on the free and
   starter plans.

Two failures that look like bugs and are not:

- **Confirmation emails point at `localhost`** → step 4 of the first deploy was
  skipped. Fix it in Supabase; no deploy needed.
- **Every authenticated route 500s on a fresh deploy** → the database was never
  migrated. Run `upgrade-db` against the session pooler.
